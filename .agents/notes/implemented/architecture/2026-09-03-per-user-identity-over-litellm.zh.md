# Agent Note: 基于 LiteLLM 的按用户身份

Status: implemented

[English](2026-09-03-per-user-identity-over-litellm.md) | 中文

## 问题

Web 界面是为单个操作者构建的。它绑定回环地址，用本进程打印的启动令牌认证浏览器，维护一份全局工作区注册表，并在每次模型请求上发送同一把已配置的提供方密钥。因此，想共用一套部署的团队会共用所有要紧的东西：一个人的工作区就是所有人的工作区，而每个人的模型花费都落在同一个账户上。harness 无法分辨两个用户，因为 harness 里根本没有用户这个概念。

与此同时，前置多家模型提供方的部署往往已经在运行 [LiteLLM](https://docs.litellm.ai) 代理，而它确实有这个概念：它签发虚拟密钥，知道每把密钥可请求哪些模型，按密钥执行预算，并核算花费。多用户 harness 需要的每一项事实，那里都已经存在。

## 决策

系统中只有一套身份，且由代理拥有。LiteLLM 虚拟密钥既是某人登录所用的凭据，也是其模型请求携带的凭据，harness 不再自建账户系统。

由四个包承担这一点：

- **`dsh-principal`**（`packages/identity/principal`）是「这份工作属于谁」的服务定义。提供方实现 `authenticate(request)`——同步的，因为载体在任何处理器运行之前就要答复请求——以及 `required`。`AsyncLocalStorage` 绑定具体实现在抽象类上而非归提供方所有：两个各持一份存储的提供方会彼此对对方的消费方不可见，因此该存储是接缝的身份。`PrincipalId` 通过一套狭窄语法打上品牌（小写、无点、无分隔符、不超过 128 字符），因为它为路径段与存储键寻址。
- **`dsh-litellm-client`**（`packages/litellm/litellm-client`）是代理管理客户端。每个方法都接收它应当以之行事的密钥；没有管理员凭据，也没有环境中的进程密钥，因为一个服务多位已登录用户的进程绝不能混淆他们的权限。
- **`dsh-litellm-auth`**（`packages/litellm/litellm-auth`）是主体提供方：位于 `/auth/litellm` 的宿主渲染登录页、一张内存会话表，以及浏览器据以登录的路由。
- **`dsh-llm-litellm`**（`packages/llm/llm-litellm`）是 `litellm` 提供方路由。其凭据规则就是本包的约定：绑定主体的密钥，否则是供无人发起的工作使用的已配置 `apiKeyEnv` 引用。配置无法颠倒该顺序。

`dsh-litellm-web`（`packages/bundle/litellm-web`）把这三者挂载到 `dsh-web-app` 之上。

两个既有包改为读取该接缝：

- **`dsh-client-connection`** — 挂载主体接缝会*替换*启动令牌浏览器会话，而不是叠加在其上。两者回答不同的问题（「这是不是本进程打开的那个浏览器」与「这是哪位用户」），而多用户部署无法分发启动令牌，因此同时要求两者会让除操作者之外的每位用户都无法访问。此后应用文档以未认证方式提供，因为登录页是浏览器在拥有任何身份之前必须抵达的文档，而它可能行使的每项权限都位于 `/api` 之后。`runAuthenticated` 在分发周围绑定请求的用户，因此请求启动的会话轮次在其每次 await 中都保持该绑定。
- **`dsh-workspace`** — 记录携带 `owner`，注册表在创建时打上它，`get`、`list` 与 `resolveByPath` 按绑定主体过滤。对既有登记的复用是按所有者进行的，因此两位用户打开同一目录时各自得到自己的工作区，而不是共享一份会话账目。域版本由 2 升至 3。

可见性规则是有意不对称的。未绑定主体时——没有接缝，或并非由请求发起的工作——所有记录可见，这就是该注册表一直以来的单操作者行为。绑定主体时，只有该主体的记录可见，且**无所有者的记录不在其中**。把登录之前的记录分享给每位已登录用户，恰恰是按用户工作区要防止的结果，因此早于登录的注册表把其记录留给未认证的 CLI。

## 会话持有密钥，所以会话不持久化

会话是本进程内存表中的一枚不透明 256 位随机令牌。不存在签名载荷，因为只会与表项比对的值不携带任何可伪造的声明。其后果是重启 harness 会让所有人退出登录，而这是被接受的代价：持久会话将不得不持久保存每位用户的 LiteLLM 密钥才能在重启后继续服务其请求，而这里没有任何东西把密钥写入磁盘。

## 备选方案考量

**把 LiteLLM 配置为 `dsh-llm-pi-ai` 上的手工声明路由。** 该适配器已经能对任意网关说 `openai-completions`，因此触及 LiteLLM 代理完全不需要新代码——对单操作者部署而言这就是正解。但它不能是此处的答案，因为其凭据经凭据接缝来自 `apiKeyEnv`，那是按部署而非按请求的。本次改动的全部要点正是一把随发问者而变的密钥。

**让凭据接缝理解主体，而不是让适配器理解。** 一个对已配置引用返回当前主体密钥的 `CredentialProvider`，能在不改动任何适配器的前提下让每个适配器都具备按用户认证，这确实很有吸引力。它被否决是因为 `credentials` 是单一 Cordis 服务：理解主体的提供方将不得不包裹并替换 `credentials-local`，于是部署无法为一个提供方选择按用户路由、而为另一个使用部署密钥；而一个引用随调用方悄悄解析为不同的值，恰恰是 `AGENTS.md` 在包边界处禁止的隐式默认。

**在既有浏览器会话 cookie 之上叠加登录。** 同时保留两者意味着用户既需要启动令牌*又*需要虚拟密钥。启动令牌只打印一次、打印到操作者的终端，且无法分发；要求它会让这项功能对其所服务的每个人都不可用。

**按用户的存储根，而不是按记录的所有者。** 分隔持久树——`sessions/`、`storages/`、附件——会比过滤共享注册表更彻底。存储后端在启动时从 `dshHomePath(...)` 一次性解析其根，因此按用户的根要么意味着按已登录用户一棵插件子树，要么意味着一个理解主体的后端，两者都比本次改动更大。记录级所有权是诚实的那一半，也是本次交付的内容；剩下的一半在「后果」中点明。

**客户端登录视图。** React 应用在 `/api` 接受请求之前无法加载，因此内置于其中的登录表单无论如何都需要未认证地提供应用包。宿主渲染的页面无需任何东西即可加载，代价是忽略主题与 locale 插件。

## 后果

它带来了什么：一套共享部署，其中每个人的工作区归其本人所有，并且由代理——而非 harness——执行他们可用哪些模型、可花多少，并把花费记在他们名下。新增一个人就是给他签发一把密钥；移除一个人就是吊销它。两者都不是 harness 操作，因此代理仍是账户唯一的存放之处。

它的代价：

- **重启会让所有人退出登录**，这是绝不把密钥写入磁盘的价钱。
- **会话无法跨第二个进程存活。** 同一地址背后的两个 harness 进程不共享该表。Web 界面今天是单进程；一旦不是，这就会成为现实问题。
- **持久会话数据仍是同一棵树。** 注册表分隔的是每个人**看到**什么；其下的会话日志与附件共用同一个 harness home，因此具备文件系统访问权限的运维者可以读到所有人的。按用户的存储根仍是这个问题中未解的一半。
- **登录时有效的密钥在整个会话内被信任。** 代理只被问一次。此后被吊销的密钥在其会话结束前仍能在此认证，届时拒绝在用户下一次模型请求时来自代理。
- **工作区域 v3 拒绝 v2 介质。** 发布前姿态：后端拒绝旧的落盘格式，因此既有注册表被丢弃而非迁移。
- **`dsh-client-connection` 现在有两种认证姿态。** 挂载主体提供方的组合会隐式获得多用户行为，这正是要点，但也是由一行挂载带来的巨大行为变化。

## 测试

`dsh-litellm-auth` 的 `tests/routes.spec.ts` 在真实 webserver 上以真实 HTTP 驱动，密钥检查背后是脚本化代理，覆盖登录、拒绝、JSON 形式、登出与会话过期。`dsh-llm-litellm` 的 `tests/plugin.spec.ts` 是凭据规则被证明之处：绑定主体的密钥抵达代理而已配置的引用没有，未绑定的请求使用该引用，两个主体各自收到自己的目录。`dsh-workspace` 的 `tests/per-user.spec.ts` 覆盖打标、按所有者列举、同一目录的按所有者复用、跨重启存活以及无所有者记录规则。`dsh-client-connection` 的 `tests/principal-gate.host.spec.ts` 覆盖被替换的姿态、未认证的应用文档，以及绑定在 `/api` 处理器内部确实生效。

没有录制会话快照变更：这里没有任何东西改变模型可见内容。路由自身的线上行为由 `tests/adapter.spec.ts` 针对脚本化 SSE 代理覆盖，而不是真实 API e2e，因为 LiteLLM 代理并不是 CI 环境的一部分。
